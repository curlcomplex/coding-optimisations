Verdict for this treatment: **reject for the current small issue-worker workload.** It does not meet the >=15% materiality gate and moved total/input/output tokens in the wrong direction despite equal acceptance. The faster wall time is secondary and based on only four accepted tasks per arm.

Interpretation limit: sqz activated only eight times across four treatment tasks. These fixtures did not produce large repetitive logs, so this does not disprove sqz's value for log-heavy workloads. It does answer the first-round question for ordinary bounded C++/UI issue workers: there was insufficient compression opportunity to overcome variance/overhead. Do not install this treatment in production on this evidence. A future separate log-heavy benchmark is warranted only if that workload itself is important enough to optimise; do not keep rerunning the same small tasks to chase a favourable number.
