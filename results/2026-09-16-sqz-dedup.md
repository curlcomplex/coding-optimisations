# sqz exact-repeat dedup after RTK — completed 16 September 2026

## Verdict

**The eight-trial coding benchmark is complete. No additional compression or attributable whole-task saving was demonstrated. Do not adopt this adapter.**

The real sqz binary passed the independent first/repeat/changed-content/expansion/fresh-role fidelity gate. In the coding cohort, however, only four eligible outputs reached sqz; none repeated. Every returned stdout was byte-identical to its RTK input. The on-arm's lower raw token total is therefore NOT evidence of sqz compression savings. Paired totals varied widely and one independent reviewer rejected an on-arm patch. This result does not establish that dedup never helps on other workloads.

The treatment invokes real upstream sqz but forwards only its exact-repeat references. First outputs and any lossy formatter output return the original RTK bytes instead. A ref is allowed only if the complete identical text was previously delivered as a tool result in that same role's rollout; compaction invalidates prior sightings. Every worker/reviewer has fresh stores. Exact expansion, stderr and exits are preserved. Recovery hints and any expansion calls would count in treatment usage.

The existing private Mac controller and shared CLI queue executed the whole cohort in one job, completed at 18:29 UTC. No intermediate model failures/restarts or selective replacement of rows occurred. All 94 lab tests passed on the Mac in 3.252 seconds before inference. The model batch took 1,156.52 seconds including setup/tests; worker/reviewer time is separately itemised below.

## Mechanism and coverage evidence

Control executed 45 RTK wrapper commands; treatment executed eight. Treatment invoked sqz four times; all four exited zero. There were zero sqz refs, zero expansions and zero compressor error/timeout fallbacks during coding. Treatment wrapper stdout was 8,420 bytes before and 8,420 after the layer; control was 45,100 before and after. These byte counts describe the intercepted wrapper surface only, not all shell/MCP output and not model-token totals.

Inspection confirms that on-arm workers primarily selected ordinary shell/Serena paths, rather than an adapter failure silently swallowing output. Optional tool choice varied despite identical initial instructions; it is not evidence that sqz reduced the number of RTK calls, since no dedup result changed model-visible text. The adapter does not intercept arbitrary shell commands or Serena results. Do not claim this is a broad transparent sqz integration.

The zero-inference real-binary gate separately exercised the intended benefit: a 7,682-byte first result remained exact; its identical second delivery became a 119-byte ref plus recovery hint; `sqz expand` returned all 7,682 original bytes. Changed content and a fresh role returned full originals. This is 98.45% less output for that specific repeat, **not** whole-task savings. Reading the ref and then expanding it costs more bytes than receiving the raw result once. No coding agent encountered a ref in the live cohort, so live recovery behaviour remains untested.

## Quality finding retained, not silently reclassified

UI repetition 1 on passed every runtime test, but Luna rejected `Array.prototype.at` because Serena reported TS2550 under its inferred TypeScript library. This verdict and the entire 457,585-token attempt remain in the original failed-review accounting.

The frozen fixture has no tsconfig or explicit TypeScript library target and runs Node's type-stripping tests; its own JavaScript reference test also uses `.at`. Consequently this is a recorded reviewer rejection, **not yet a proven violation of a declared library target**, and must not be described as a sqz-caused code regression. Neither its worker nor reviewer invoked sqz. No reviewer gate was weakened or post-hoc accepted flag rewritten to manufacture a saving. Future fixture maintenance should pin the intended TypeScript type-check environment before a new cohort, separately from these immutable results.
